## Hugo + Stack 的 GitHub Actions 编译可行性（专项查证）

- 产出文档：`HUGO_STACK_GITHUB_ACTIONS.md`（仓库根目录）。结论：**可以，官方有现成 workflow 可抄**。
- **坑 1（致命）**：Stack v4 的 `layouts/_partials/head/style.html` 用 `$sass | toCSS` 且**未指定 transpiler** → 走默认 `libsass` → **只有 Hugo extended 版内置**。必须下载 `hugo_extended_0.168.0_linux-amd64.tar.gz`（注意不是 `hugo_0.168.0_...`）。且 LibSass 在 **Hugo v0.153.0 已弃用**（"tpl/css: Deprecate libsass in favor of dartsass"），而 Stack v4.0.3（2026-05-25）changelog 里完全没提 Dart Sass 迁移 → 主题侧有技术债，未来 Hugo 移除 libsass 时需主题方自行改造。
- **坑 2**：Stack v4 是 Hugo Module（`go.mod` 里**零依赖**，`go 1.17`），CI 需 `actions/setup-go`（官方 workflow 用 `if: hashFiles('go.mod') != ''` 条件判断，缺 Go 直接构建失败）。→ 建议改用 **git submodule** 方式引入（不用 Go、版本天然锁定、构建不依赖网络）。
- **坑 3**：Stack v4.0.0（2026-04-26）是大重构：模板路径全改（`layouts/_default/` → `layouts/`、`partials` → `_partials`、`shortcodes` → `_shortcodes`）、配置 YAML→TOML（`config/_default/` 多文件）、**语言码 `zh-cn` → `zh`**、`hidden: true` → `build.list: never`、`sidebar.avatar` 改字符串、favicon 移到 `assets/`、`imageProcessing.cover` → `thumbnail`、Vibrant.js 移除。最低 Hugo `0.157.0`。
- 中文博客要点：`hasCJKLanguage = true` 必须开（否则 `.Summary`/`.WordCount` 对中文不正确）。评论用 Giscus（需先开 GitHub Discussions 拿 repoID/categoryID）。
- **部署**：仓库名 `11os.github.io` 是用户站 → 根路径，**不需要 base path**。用官方 `configure-pages@v6` + `upload-pages-artifact@v5` + `deploy-pages@v5` 链路 → **不需要 .nojekyll**（不经 Jekyll）；若继续用 `gh-pages` 分支源则必须加 `.nojekyll`。
- 本机环境：Node v22.22.2、npm 10.9.7，**无 yarn / 无 go / 无 hugo**。Hugo 项目完全不需要 Node/yarn（顺带解决 lockfile 冲突问题）。本地需装 `hugo_extended_0.168.0_windows-amd64.zip` 并加 PATH。
- 官方 Hugo workflow 参考（2026-10-10 更新）：https://gohugo.io/host-and-deploy/deploy-to-github-pages/ ；Stack v4 升级指南：https://stack.cai.im/guide/upgrade-to-v4

## 发布链路修正：gh-pages（legacy）→ 官方 deploy-pages

- **现象**：文章改完推送后 CI 红，`deploy` job 失败。job log API 无 token 时 403，但 `check-runs/{id}/annotations` 免鉴权拿到了错误原文：
  `Failed to create deployment (status: 400) ... Invalid deployment branch ... Deployments are only allowed from gh-pages`。
- **原因**：仓库 Pages 源是 **legacy / `gh-pages` 分支**，官方 `deploy-pages` 必然 400；此前 `Deploy to GitHub Pages` 步骤挂着 `continue-on-error: true`，一直是**假绿**，真正发布的是 `deploy-branch`（JamesIves action 推 gh-pages 分支，再由 GitHub 的 pages build 发布）。上一个会话的「简化 CI」把 `deploy-branch` 删了又没推，直到这次推上去才暴露 → 站点一度停更。
- **处理（2026-10-26）**：
  1. 用本机 git 凭据调 API（`git credential fill` 从 GCM 取出 token，**未打印明文**，40 字符，认证为 `11os`）：`PUT /repos/11os/11os.github.io/pages` body `{"build_type":"workflow"}` → 源切成 GitHub Actions。
  2. `github-pages` 环境的 deployment branch policy 自动放行 `master`（`/repos/{o}/{r}/environments/github-pages/deployment-branch-policies`）。
  3. workflow 精简为 `build` + `deploy` 两个 job，删掉 `deploy-branch`、`continue-on-error` 和多余的 `Upload site artifact` 步骤。commit `698ae50`，实测 build/deploy 全绿。
  4. 删除远端 `gh-pages` 分支（`git push origin --delete gh-pages`），删除后站点仍正常（`build_type=workflow` 下该分支已无关）。
- **排查手法备忘**：无 token 也能拿 CI 错误原文 —— `GET /repos/{o}/{r}/actions/runs/{id}/jobs` 取 job 的 `check_run_url`，再 `GET .../annotations`。
- **遗留**：远端还有一个 2021-09-01 的 `docs` 分支（含 `.travis.yml` / `package.json` / `yarn.lock`，VitePress + Travis 时代产物），疑似同样可删，等用户确认。
